# Dataset download, restore and integrity

| Dataset | Release | Restore command | Free space |
|---|---|---|---|
| **fleetcan-sim-2.0** (recommended) | `dataset-fleetcan-sim-2.0`, 8 parts, 11.6 GB | `scripts/download_fleetcan_sim_2_0.sh DEST` | about 25 GB |
| fleetcan-sim-dataset-1.0 | `dataset-fleetcan-sim-dataset-1.0`, 7 parts | `scripts/download_fleetcan_sim_dataset_1_0.sh DEST` | about 22 GB |
| fleetcan-sim-scale-1.0 (raw source of dataset-1.0) | `dataset-fleetcan-sim-scale-1.0`, 9 parts, 13.87 GB | `scripts/download_fleetcan_sim_scale_1_0.sh DEST` | about 35 GB |

The repository is public. Every script needs bash, `tar`, `zstd`, `sha256sum` or `shasum`, `python3` and the GitHub
CLI `gh`. Each script verifies the archive parts against the checksums committed in `results/dataset_release/<name>/`,
then every extracted file against the dataset's `SHA256SUMS`, and fails closed on any mismatch.

## fleetcan-sim-2.0

The dataset is described in `results/datasets/fleetcan-sim-2.0/README.md`, and its generation in
[m13_fleetcan_sim_2_0_generation.md](m13_fleetcan_sim_2_0_generation.md). Reference values are in
`results/datasets/fleetcan-sim-2.0/reference.json`:
* 1,298 files, 11,611,562,499 bytes;
* 645 sessions;
* `SHA256SUMS` SHA-256 `0fd37bb31233c235712791df96ebe3ccd0948e781fd9e934c3b737059794b8b1`.

To re-check a restored copy:

```bash
cd DEST/fleetcan-sim-2.0 && shasum -a 256 -c --quiet SHA256SUMS
```

Detector input: use only `Timestamp`, `Vehicle_ID`, `Arbitration_ID`, `DLC` and `Data`. `Class`, `SubClass`,
`Attack_ID`, `Campaign_ID` and all summary tables are labels and metadata for evaluation.

## fleetcan-sim-scale-1.0

### Dataset

**fleetcan-sim-scale-1.0** is an expanded multi-vehicle **synthetic CAN dataset generated by the SUMO + synthetic CAN
testbed** in this repository, for fleet-level coordinated-attack research (FLEET-GUARD). Mobility comes from SUMO, CAN
traffic from a synthetic per-vehicle model and a logical 500 kbit/s CAN bus model, and transport from Linux vCAN. It is
**not** real vehicle CAN data.

| Property | Value |
|---|---|
| Sessions | 835 = 167 configurations × 5 repetitions (frozen matrix `fleetcan-sim-scale-1.0-matrix-v1`) |
| Fleet sizes | N = 20, 50, 100, plus a route-source bridge at N = 10 (G0) |
| CAN frames | 444,333,222 |
| Content | raw observable CAN data + separate ground truth + metadata/provenance + generator validation; **no precomputed FLEET-GUARD descriptors** |
| Source size | 26,740 hashed files, 21,727,934,640 bytes |
| Matrix SHA-256 | `9fc005de3f9b712045c7eec5c610043a375ab2dad362fff5b54a092a17a1e735` |
| Dataset `SHA256SUMS` SHA-256 | `5d5418b1ca9a4107818a83e03a5dea4a4ea83d1c36354fa668fcc5cb0242de70` |
| `FREEZE.json` SHA-256 | `c714b4790121a469e28b81e2a25879f1fa61d059fb9222e9a34b5d009a58f740` |
| Generator / schema | 1.3.0 / 1.0 |
| Generation report | `docs/m10_expanded_dataset_generation.md` |

The baseline **fleetcan-sim-1.1** (N = 2/5/10) is a separate, immutable component. It is not part of this release.

### Download and restore

The GitHub release `dataset-fleetcan-sim-scale-1.0` of the repository `iyadsec/fleet-can-dataset` holds the
archive. It is 9 parts, 13.87 GB in total.

```bash
git clone https://github.com/iyadsec/fleet-can-dataset.git && cd fleet-can-dataset
scripts/download_fleetcan_sim_scale_1_0.sh /path/to/destination
```

**Requirements:** bash, `tar`, `zstd`, `sha256sum` or `shasum`, and the GitHub CLI `gh`. You need about 14 GB for the
download and about 22 GB for the dataset, at the same time. After a successful restore the downloaded parts are deleted
unless you pass `--keep-archive`.

If the parts are already downloaded, you can restore without the network:

```bash
scripts/download_fleetcan_sim_scale_1_0.sh /path/to/destination --from-dir /path/to/parts
```

The result is `/path/to/destination/fleetcan-sim-scale-1.0/data/`, which has exactly the frozen on-disk layout:

```
data/raw/FCS10_<config>_R<rep>/            can_frames, vehicle_states, unmatched_captures   (observable)
data/ground_truth/FCS10_<...>/             labels, attacks, attack_frames, campaigns, campaign_membership,
                                           campaign_overlap, dropped_frames, replay_map      (ground truth)
data/metadata/FCS10_<...>/                 metadata.json (provenance tags), bus_stats.json, config_snapshot
data/validation/FCS10_<...>/               validation_report.json / .md
data/generated_sumo/FCS10_<...>/           generated SUMO routes
data/m10_configs/FCS10_<...>/              session configuration derived from the frozen matrix
data/final/fleetcan-sim-scale-1.0/         SHA256SUMS, FREEZE.json, manifest.jsonl, statistics, validation summary, provenance/
```

### Integrity: two levels

**1. Archive integrity.** The downloaded `fleetcan-sim-scale-1.0-archive-SHA256SUMS` must be byte-identical to the copy
committed in this repository (`results/dataset_release/fleetcan-sim-scale-1.0/`). Every part must then match it. This
proves the transfer is complete and uncorrupted. It says nothing about the scientific content.

**2. Scientific dataset integrity.** Every extracted file must match the authoritative dataset `SHA256SUMS` from the M10
freeze. That file's digest is `5d5418b1…de70`, and it is identical to `results/datasets/fleetcan-sim-scale-1.0/SHA256SUMS`
in this repository. The restore also checks that there are 835 sessions and the expected file count. This proves the
restored data are the frozen dataset, byte for byte.

The restore script runs both levels and **fails closed**: it stops at the first mismatch and leaves nothing at the
destination. To re-check a restored copy at any time:

```bash
cd /path/to/destination/fleetcan-sim-scale-1.0/data
sha256sum -c --quiet final/fleetcan-sim-scale-1.0/SHA256SUMS      # macOS: shasum -a 256 -c --quiet ...
```

### Detector-side use (FLEET-GUARD): what may and may not be input

* **Observable CAN data:** `raw/<sid>/can_frames`. Build detector inputs from the observable frame fields only:
  timestamps or bus times, `vehicle_id`/`channel`, `can_id`, `dlc`, `payload`. Use an **explicit feature allow-list**.
  `raw/<sid>/vehicle_states` is SUMO simulator state (speed, position, ...), not CAN-observable. It is not detector input
  for a CAN-based detector.
* **`scenario_id` must not be used.** It is present in `raw/<sid>/can_frames` (schema 1.0) for compatibility and
  provenance, but it is a scenario label (S0–S3). It must not be a detector feature and must not influence
  preprocessing. `session_id` and `frame_uid` are identifiers, not features.
* **Never detector input:** everything in `ground_truth/`, and the provenance in `metadata/` and `m10_configs/`. That
  covers attack labels, attack and campaign IDs, coordinated flags, configured campaign or attack times, K, member
  lists, scenario identity, the configuration ID, profile composition and the seed. Use it for evaluation only, joined
  after detection.
* **No descriptors are included.** The FLEET-GUARD pipeline computes them from `raw/`.

* owner and group 0, numeric IDs;
* atime/ctime not stored;
* mtime and mode kept;
* `zstd -3 -T4`;
* parts of 1,610,612,736 bytes (GitHub release assets must be under 2 GiB).

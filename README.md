# fleet-can-dataset

Testbed and dataset for PhD research on **fleet-level detection of coordinated CAN attacks** (FLEET-GUARD). The dataset
is a **synthetic CAN dataset generated by the SUMO + synthetic CAN testbed** in this repository. It contains
synchronized CAN traffic from fleets of simulated vehicles, with attacks and coordinated campaigns, and with the
ground truth stored separately. It is not real vehicle CAN data.

This repository covers data generation and ground truth. The FLEET-GUARD detector is not part of it.

## Dataset: fleetcan-sim-scale-1.0

| Property | Value |
|---|---|
| Fleet sizes | N = 20, 50, 100, plus an N = 10 route-source bridge (G0) |
| Sessions | 835 = 167 configurations × 5 repetitions (frozen matrix `fleetcan-sim-scale-1.0-matrix-v1`) |
| CAN frames | 444,333,222 |
| Scenarios | S0 benign, S1 isolated attack, S2 independent attacks (hard negatives), S3 coordinated campaigns, mixed |
| Attacks | flooding, fuzzy, malfunction, replay |
| Timing | simultaneous; 0.5 / 2 / 10 s stagger; partial overlap; bounded spread 0.5 / 2 / 10 s; 0.1 s replay probe |
| Content per session | raw observable CAN data (`raw/`), separate ground truth (`ground_truth/`), metadata/provenance (`metadata/`), generator validation (`validation/`) |
| Descriptors | none; the FLEET-GUARD pipeline computes them from `raw/` |
| Size | 26,740 files, 21.7 GB (archive: 9 parts, 13.87 GB) |
| Integrity | `SHA256SUMS` SHA-256 `5d5418b1ca9a4107818a83e03a5dea4a4ea83d1c36354fa668fcc5cb0242de70`; matrix SHA-256 `9fc005de3f9b712045c7eec5c610043a375ab2dad362fff5b54a092a17a1e735` |
| Generator / schema | 1.3.0 / 1.0 |

## How to download and restore the dataset (step by step)

The dataset is published as the GitHub release `dataset-fleetcan-sim-scale-1.0`: 9 compressed archive parts (13.87 GB)
plus checksums. The restore script downloads the parts, verifies them, uncompresses them and verifies every file. It
works on Linux and macOS.

**Step 1: check free disk space.** You need about **35 GB** free (14 GB download + 22 GB dataset). The download is
deleted automatically after a successful restore.

```bash
df -h ~
```

**Step 2: install the tools.**

```bash
# Ubuntu / Debian
sudo apt-get install -y git zstd tar gh
# macOS (Homebrew, https://brew.sh); tar and shasum are built in
brew install git zstd gh
```

**Step 3: log in to GitHub.** The repository is private.

```bash
gh auth login        # choose: GitHub.com -> HTTPS -> Login with a web browser
```

**Step 4: clone this repository.** The clone contains the restore script and the reference checksums; it does not
contain the data. Use a folder outside OneDrive or iCloud.

```bash
mkdir -p ~/research && cd ~/research
git clone https://github.com/iyadsec/fleet-can-dataset.git
cd fleet-can-dataset
```

**Step 5: download, uncompress and verify (one command).**

```bash
scripts/download_fleetcan_sim_scale_1_0.sh ~/fleetcan_data
```

The script:
1. downloads all release assets;
2. checks that the archive checksum file is identical to the committed copy in `results/dataset_release/`;
3. checks the SHA-256 of all 9 parts;
4. joins, decompresses (zstd) and extracts (tar) them;
5. checks all 26,740 files against the dataset `SHA256SUMS` and confirms 835 sessions.

**Step 6: confirm success.** The last line must read:

```
SUCCESS: fleetcan-sim-scale-1.0 restored to .../fleetcan_data/fleetcan-sim-scale-1.0 (26740 files verified ..., 835 sessions)
```

If any check fails, the script prints `FAIL: ...`, restores nothing and exits non-zero. Re-run it in that case.

**Step 7: use the data.** The dataset is in:

```
~/fleetcan_data/fleetcan-sim-scale-1.0/data/
  raw/FCS10_<config>_R<rep>/can_frames.parquet   <- FLEET-GUARD input (observable CAN)
  ground_truth/FCS10_*/                          <- evaluation only
  metadata/FCS10_*/metadata.json                 <- session info (N, K, scenario, ...), evaluation only
  validation/  generated_sumo/  m10_configs/  final/fleetcan-sim-scale-1.0/
```

Treat it as read-only and write FLEET-GUARD outputs to a separate folder.

**Optional:**

```bash
# re-check a restored copy at any time (no output = all files match; macOS: shasum -a 256 -c --quiet ...)
cd ~/fleetcan_data/fleetcan-sim-scale-1.0/data && sha256sum -c --quiet final/fleetcan-sim-scale-1.0/SHA256SUMS

# restore from parts you already have (no download)
scripts/download_fleetcan_sim_scale_1_0.sh ~/fleetcan_data --from-dir /path/to/parts

# keep the downloaded parts after restoring
scripts/download_fleetcan_sim_scale_1_0.sh ~/fleetcan_data --keep-archive
```

More detail on the two integrity levels and on provenance: [docs/dataset_download.md](docs/dataset_download.md).

## Detector-safe use (FLEET-GUARD)

* Build FLEET-GUARD inputs from `raw/*/can_frames` using an explicit allow-list of observable fields (timestamps,
  `vehicle_id`/`channel`, `can_id`, `dlc`, `payload`).
* `scenario_id` is present in `can_frames` for provenance and must not be used as a feature.
* `ground_truth/` and the metadata (labels, campaign IDs, coordinated flags, configured times, K, scenario) are for
  evaluation only.

## What is real and what is synthetic

| Layer | Source | Nature |
|---|---|---|
| Mobility (speed, acceleration, position, lane, route) | SUMO 1.28 via TraCI | Simulated (synthetic road network and routes) |
| CAN signals (RPM, gear, pedal, brake, steering) | `src/can_generator.py` | **Synthetic model** derived from SUMO state |
| CAN IDs, layouts, scaling | `dbc/generic_vehicle.dbc` | **Defined by this project.** Not OEM CAN IDs |
| Bus timing (duration, arbitration, queueing, drops) | `src/bus_model.py` | **Logical model** of Classical CAN at 500 kbit/s, not a physical-layer simulation |
| CAN transport + capture | Linux SocketCAN **vCAN** | Real kernel frame delivery; **no** bus behaviour of its own |
| Attacks | `src/attack_engine.py` + `config/m2/` | **Injected** from configuration, single vehicle |
| Campaigns | `src/campaign_scheduler.py` + `config/m3/campaigns_*.yaml` | **Experimentally constructed** from configuration |

The generated traffic is **not real vehicle CAN traffic**. SUMO does not simulate CAN.

## Architecture

```
SUMO --TraCI--> SumoController --VehicleState(t)--> VehicleCanGenerator (one per vehicle, DBC + profile)
     --TxFrame(generation time)--> AttackEngine (inject / modify, ground truth attached)
     --> CanBusModel per vehicle (bit-exact duration, ID arbitration, queues, drops)
     --BusTx(tx_start, tx_end)--> CanTransport (SocketCAN, ECU and attacker sockets) --> vcanN
     --> CanCapture (separate socket per channel)
     --CapturedFrame--> recorder.associate (k-th sent == k-th captured, ID+payload checked)
     --> data/raw/<session>/can_frames.csv          (observations)
     --> data/ground_truth/<session>/*.csv         (labels, campaigns: separate files)
     --> data/metadata/<session>/metadata.json     (+ config snapshot with SHA-256)
     --> data/validation/<session>/validation_report.{json,md}
```
Details: [docs/architecture.md](docs/architecture.md), [docs/dataset_schema.md](docs/dataset_schema.md),
[docs/timing_model.md](docs/timing_model.md).

## Configuration

* `config/experiment.yaml`: IDs, seed, SUMO step and duration, transport, output.
* `config/vehicles.yaml`: vehicle **profiles** (DBC, message periods/offsets, signal mapping, synthetic
  model parameters) and the fleet (vehicle → profile; channel `vcan{index}` by list order).
  Profiles are separate from code, so heterogeneous fleets need only new profiles/DBCs.
* `config/vehicles.yaml` → `bus:` per profile: stuffing, queue_limit, drop_policy, node_queue_order;
  `nominal_bitrate` drives the bus model. `can.bus_model: logical | ideal` in the experiment file.
* `config/m2/attacks_*.yaml`: one attack per file (vehicle_01); `config/attacks.yaml` and
  `config/campaigns.yaml` are empty.

## Reproducibility

Each session stores the seed, SUMO command and version, Python and package versions, kernel, git commit
(and dirty flag), SHA-256 and a copy of every config/DBC/SUMO input, and the time-base definition.
With `realtime: true`, SUMO-timeline content is deterministic for a given seed. Capture timestamps
reflect host execution and are not.

## Limitations (model scope; first recorded in Milestone 2)

* Bus effects come from a logical model (exact frame length, ID arbitration, queues, drops), not
  from vCAN. Error frames, retransmission, bus-off and bit-level effects are not modelled; the same
  ID sent by two nodes at once is serialised instead of causing a bit error.
* Synthetic profiles A/B/C (Milestone 5); seeded switch-on offsets and ±1 % ECU release jitter (Milestone 5.1); no sensor noise.
* Campaign delays are exact on the logical timeline; transmission/capture layers are reported separately.
* Frame expiry uses one max age per bus (100 ms in Milestone 3 fleets), not per-message deadlines.
* Capture jitter depends on host/VM load; it is measured (`capture_offset_us`), never used as ground truth.
* vCAN interfaces must be recreated after reboot.

# fleet-can-dataset

This repository contains the testbed and datasets for PhD research on **fleet-level detection of coordinated CAN
attacks** (FLEET-GUARD) and the **adversarial robustness of fleet-level correlation** (ROBUST-FLEET-GUARD).

The data are **synthetic CAN data** generated by the SUMO + synthetic CAN testbed in this repository: synchronised CAN
traffic from fleets of simulated vehicles, with injected attacks and coordinated campaigns, and with the ground truth
stored separately. They are not real vehicle CAN data.

| Dataset | What it is | Use it for | GitHub release |
|---|---|---|---|
| **fleetcan-sim-research-1.0** (recommended) | Derived research release: detector-safe CAN observations (Parquet + CSV), separate ground truth and metadata, FLEET-GUARD 24-D descriptors, complete results, validation, reports | experiments and evaluation | `dataset-fleetcan-sim-research-1.0` (18.9 GB) |
| fleetcan-sim-scale-1.0 | Frozen source dataset: raw generator output (raw CAN + ground truth + metadata) | provenance and regeneration checks | `dataset-fleetcan-sim-scale-1.0` (13.9 GB archive) |

The two releases contain the same 835 sessions and the same 444,333,222 CAN frames. The research release changes no
frame, timestamp, label or configuration; it only reorganises, separates, documents and validates them.

Every session ID, for example `FCS10_N050_S3_replay_K010_partial_R3`, appears as one directory in each of the five
`data/` areas. The ID encodes the fleet size (N050), scenario (S3), attack family (replay), campaign size (K010),
timing pattern (partial) and repetition (R3). G0 sessions start with `FCS10_G0_`.

### What each folder contains

**`data/raw_parquet/` and `data/raw_csv/` — detector-facing observations.** One row per CAN frame.

| Column | Type | Meaning |
|---|---|---|
| `frame_index` | int64 | row number in the source session; join key to ground truth (not a feature) |
| `timestamp_ns` | int64 | observable bus time: end of the frame on the logical CAN bus (shared simulation clock, ns) |
| `vehicle_id` | string | vehicle / bus; grouping key (not a feature) |
| `can_id` | string | 11-bit CAN identifier, e.g. `0x0C1` |
| `dlc` | int8 | data length code 0–8 |
| `data` | string | payload as upper-case hex (`2·dlc` characters) |

These files contain nothing else: no session ID, scenario, labels, campaign IDs or host clock. Parquet and CSV hold
the same table (verified for every session). The CSV files are gzip-compressed and can be read directly
(`pd.read_csv(path, dtype={"can_id": str, "data": str, "vehicle_id": str}, keep_default_na=False)`).

**`data/ground_truth/` — evaluation only.**

| File | Content |
|---|---|
| `frame_labels.*` | label of every frame (benign/malicious), attack ID, attack type, campaign ID, frame source, message |
| `attacks.*` | configured attack instances (start/end, rate, counts, seed, parameters) |
| `campaigns.*`, `campaign_membership.*`, `campaign_overlap.*` | campaigns, coordinated flag, members, configured delays, overlap |
| `attack_frames.*`, `replay_map.*`, `dropped_frames.*` | per-malicious-frame details, replay links (replayed → original frame), drops (none) |
| `attack_instances.*` | **derived**: configured and observable timing per attack (`derived_*` columns: first/last malicious frame, onset delay, first descriptor window with attack frames) |
| `window_labels.*` | **derived**: per descriptor window: malicious frame count/ratio, original majority label, any-malicious label, attack/campaign IDs |

**`data/metadata/` — never a feature.** `session.json` (scenario, N, K, family, timing, configuration, repetition,
seed, route group, generator version and commit), `vehicles.csv` (profile, ECU switch-on, route, speed),
`frame_bus_timing.parquet` (generation time, transmission start, frame bits, host capture time, channel) and
verbatim copies of the source metadata.

**`data/descriptors/` — FLEET-GUARD descriptors.** Window keys (`vehicle_id`, `window_index`, first/last frame,
`descriptor_timestamp_ns` = time of the window's last frame) and the 24 original features (`frame_count`,
`unique_can_id_count`, `can_id_entropy`, `most_common_can_id_ratio`, inter-arrival mean/std, DLC mean/std,
`byte_mean_0…7`, `byte_std_0…7`). Labels are in `ground_truth/<session>/window_labels.*` and join on
(`vehicle_id`, `window_index`).

**`results/`** — complete CSV tables over all sessions: dataset, session, vehicle, profile, scenario and fleet-size
summaries; CAN-ID, DLC, payload, inter-arrival and bus statistics; benign traffic and benign false-positive
statistics; attack instances and family summary; campaign instances and timing; temporal observability; replay
timing and links; G0 and vehicle-identity bias; descriptor statistics; ground-truth checks; data-quality issues.

**`validation/`** — source integrity (before and after export), manifest, schema, ground-truth, campaign and replay
validation; P1 metadata leakage, benign sanity check and temporal consistency; P2 replay and G0 assessments;
descriptor compatibility; test results; issue register, corrections log, unresolved issues; output integrity.

### How to download and restore (step by step)

**Step 1: check free disk space.** You need about **40 GB** free: about 19 GB of download plus 19 GB of dataset.
The download is deleted after a successful restore.

```bash
df -h ~
```

**Step 2: install the tools.**

```bash
# Ubuntu / Debian
sudo apt-get install -y git zstd tar gh python3
# macOS (Homebrew); tar, shasum and python3 are built in
brew install git zstd gh
```

**Step 3: clone this repository.** The clone contains the restore script and the reference checksums; it does not
contain the data. Use a folder outside OneDrive or iCloud.

```bash
mkdir -p ~/research && cd ~/research
git clone https://github.com/iyadsec/fleet-can-dataset.git
cd fleet-can-dataset
```

**Step 4: download, uncompress and verify (one command).**

```bash
scripts/download_fleetcan_sim_research_1_0.sh ~/fleetcan_data
```

The script:
1. downloads the release `dataset-fleetcan-sim-research-1.0`;
2. checks the archive checksum file against the committed copy;
3. checks the SHA-256 of every part;
4. decompresses and extracts the parts as a stream;
5. checks every file against `SHA256SUMS` and confirms 835 sessions in each data area.

**Step 5: confirm success.** The last line must read:

```
SUCCESS: fleetcan-sim-research-1.0 restored to .../fleetcan_data/fleetcan-sim-research-1.0 (34339 files verified against SHA256SUMS, 835 sessions in each data area)
```

If any check fails, the script prints `FAIL: ...`, restores nothing and exits non-zero.

**Step 6: use the data.** Open `reports/html/index.html` for an overview. Load data like this:

```python
import pandas as pd
root, sid = "fleetcan_data/fleetcan-sim-research-1.0", "FCS10_N050_S3_replay_K010_partial_R3"
obs  = pd.read_parquet(f"{root}/data/raw_parquet/{sid}/can_frames.parquet")      # detector input
desc = pd.read_parquet(f"{root}/data/descriptors/{sid}/descriptors.parquet")     # 24 features + window keys
lab  = pd.read_parquet(f"{root}/data/ground_truth/{sid}/window_labels.parquet")  # evaluation only
```

**Optional:**

```bash
# re-check a restored copy at any time (no output = all files match)
cd ~/fleetcan_data/fleetcan-sim-research-1.0 && shasum -a 256 -c --quiet SHA256SUMS

# restore from parts you already have (no download)
scripts/download_fleetcan_sim_research_1_0.sh ~/fleetcan_data --from-dir /path/to/parts
```

### Detector-safe use (FLEET-GUARD / ROBUST-FLEET-GUARD)

* Load every detector-side input through `scripts/detector_adapter.py` (in the release) or `research/adapter.py` (in
  this repository). It enforces an allow-list and rejects unknown or prohibited columns.
* The model input is exactly the 24 descriptor features in their frozen order.
* Ground truth (`data/ground_truth/`) and metadata (`data/metadata/`) are for evaluation only. Never use them as
  features: no scenario, session ID, labels, campaign IDs or flags, configured times, K, N, profile, route group, seed
  or host capture time.
* Vehicle and session identity may be used only for grouping and splitting. Split at session level, never at window
  level.

## What is real and what is synthetic

| Layer | Source | Nature |
|---|---|---|
| Mobility (speed, acceleration, position, lane, route) | SUMO 1.28 via TraCI | Simulated (synthetic road network and routes) |
| CAN signals (RPM, gear, pedal, brake, steering) | `src/can_generator.py` | **Synthetic model** derived from SUMO state |
| CAN IDs, layouts, scaling | `dbc/generic_vehicle.dbc` | **Defined by this project.** Not OEM CAN IDs |
| Bus timing (duration, arbitration, queueing, drops) | `src/bus_model.py` | **Logical model** of Classical CAN at 500 kbit/s, not a physical-layer simulation |
| CAN transport + capture | Linux SocketCAN **vCAN** | Real kernel frame delivery; **no** bus behaviour of its own |
| Attacks | `src/attack_engine.py` + `config/m2/` | **Injected** from configuration, single vehicle |
| Campaigns | `src/campaign_scheduler.py` + `config/m3/campaigns_*.yaml` | **Experimentally constructed** from configuration |

The generated traffic is **not real vehicle CAN traffic**. SUMO does not simulate CAN.

## Architecture

```
SUMO --TraCI--> SumoController --VehicleState(t)--> VehicleCanGenerator (one per vehicle, DBC + profile)
     --TxFrame(generation time)--> AttackEngine (inject / modify, ground truth attached)
     --> CanBusModel per vehicle (bit-exact duration, ID arbitration, queues, drops)
     --BusTx(tx_start, tx_end)--> CanTransport (SocketCAN, ECU and attacker sockets) --> vcanN
     --> CanCapture (separate socket per channel)
     --CapturedFrame--> recorder.associate (k-th sent == k-th captured, ID+payload checked)
     --> data/raw/<session>/can_frames.csv          (observations)
     --> data/ground_truth/<session>/*.csv         (labels, campaigns: separate files)
     --> data/metadata/<session>/metadata.json     (+ config snapshot with SHA-256)
     --> data/validation/<session>/validation_report.{json,md}
```
Details: [docs/architecture.md](docs/architecture.md), [docs/dataset_schema.md](docs/dataset_schema.md),
[docs/timing_model.md](docs/timing_model.md).

## Configuration

* `config/experiment.yaml`: IDs, seed, SUMO step and duration, transport, output.
* `config/vehicles.yaml`: vehicle **profiles** (DBC, message periods/offsets, signal mapping, synthetic
  model parameters) and the fleet (vehicle → profile; channel `vcan{index}` by list order).
  Profiles are separate from code, so heterogeneous fleets need only new profiles/DBCs.
* `config/vehicles.yaml` → `bus:` per profile: stuffing, queue_limit, drop_policy, node_queue_order;
  `nominal_bitrate` drives the bus model. `can.bus_model: logical | ideal` in the experiment file.
* `config/m2/attacks_*.yaml`: one attack per file (vehicle_01); `config/attacks.yaml` and
  `config/campaigns.yaml` are empty.

## Reproducibility

Each session stores the seed, SUMO command and version, Python and package versions, kernel, git commit
(and dirty flag), SHA-256 and a copy of every config/DBC/SUMO input, and the time-base definition.
With `realtime: true`, SUMO-timeline content is deterministic for a given seed. Capture timestamps
reflect host execution and are not.

## Limitations (model scope; first recorded in Milestone 2)

* Bus effects come from a logical model (exact frame length, ID arbitration, queues, drops), not
  from vCAN. Error frames, retransmission, bus-off and bit-level effects are not modelled; the same
  ID sent by two nodes at once is serialised instead of causing a bit error.
* Synthetic profiles A/B/C (Milestone 5); seeded switch-on offsets and ±1 % ECU release jitter (Milestone 5.1); no sensor noise.
* Campaign delays are exact on the logical timeline; transmission/capture layers are reported separately.
* Frame expiry uses one max age per bus (100 ms in Milestone 3 fleets), not per-message deadlines.
* Capture jitter depends on host/VM load; it is measured (`capture_offset_us`), never used as ground truth.
* vCAN interfaces must be recreated after reboot.
